## Format: pre-windowed samples

The release is **not** a raw time series. Each row is one sample for one sensor at one reference time `t0`:

| Column | Type | Meaning |
|---|---|---|
| `node_id` | int64 | Sensor index 0–206 |
| `t0_timestamp` | string | ISO-8601 reference time (naive local time) |
| `x_t-11_d0` … `x_t+0_d0` | float64 | Speed at the 12 input steps (t-55min … t) |
| `x_t-11_d1` … `x_t+0_d1` | float64 | Time of day for those steps, as `minutes / 1440` |
| `y_t+1_d0` … `y_t+12_d0` | float64 | **Target** speed at the 12 future steps (t+5 … t+60min) |
| `y_t+1_d1` … `y_t+12_d1` | float64 | Time of day for target steps |

50 columns in total. Horizons used by FlowCast: 15 min = `y_t+3`, 30 min = `y_t+6`, 45 min = `y_t+9`, 60 min = `y_t+12`.

Each reading appears in up to 24 rows. FlowCast reconstructs a single canonical matrix of shape **34,272 timestamps × 207 sensors** (`data/processed/metr_la_speed.parquet`, 9.6 MB). The reconstruction **verifies that every redundant copy of every reading is bit-identical** and that every `d1` value matches its timestamp. Every downstream phase builds its features from this matrix, so the feature pipeline has full control over what is visible at prediction time.

## Splits

The splits are chronological 70/10/20, cut **on sample index** (DCRNN convention):

| Split | Rows | Samples (t0) | First t0 | Last t0 | Missing % (owned period) |
|---|---:|---:|---|---|---:|
| train | 4,962,618 | 23,974 | 2012-03-01 00:55 | 2012-05-23 06:40 | 7.13 |
| validation | 708,975 | 3,425 | 2012-05-23 06:45 | 2012-06-04 04:05 | 6.97 |
| test | 1,417,950 | 6,850 | 2012-06-04 04:10 | 2012-06-27 22:55 | 12.09 |

Rows = samples × 207. The splits are contiguous, and train, validation and test do not share any `t0`.

**Boundary overlap (documented leakage risk).** Because the cut is on sample index, the last 12 train samples have targets that fall inside the validation period, and the last 12 validation samples have targets inside the test period. Inputs that reach back into an earlier split are legitimate, since the past is known at prediction time. Targets that reach forward into a later split are not. For this reason FlowCast assigns every timestamp to exactly one *owned period* (`data/processed/metr_la_splits.json`):

- train: 2012-03-01 00:00 → 2012-05-23 06:40
- validation: 2012-05-23 06:45 → 2012-06-04 04:05
- test: 2012-06-04 04:10 → 2012-06-27 23:55

The effect is small (12 of 23,974 train samples). Even so, model selection must drop samples whose targets cross into a later split, or at least report results with them dropped. Published DCRNN-style benchmark numbers use the splits unchanged, so for comparability we will report both.

## Missing values

Missing readings are encoded as **`0.0`**, the original DCRNN convention. The value 0 never occurs as a genuine reading. The smallest positive reading is 0.33 mph.

| Metric | Value |
|---|---|
| Overall missing | 8.11 % |
| Per sensor (min / median / max) | 6.27 % / 6.97 % / 20.10 % |
| Sensors > 20 % missing | 1 |
| Timestamps where **all 207 sensors** are missing | 2,148 (≈ 7.5 days), in 97 blocks |
| Longest single-sensor outage | 1,683 steps ≈ 5.8 days (node 70). Median sensor: 381 steps. |
| Positive readings < 5 mph | 3,378 (0.05 %). Flagged, not removed. |

Most missingness is **network-wide outages** rather than individual sensor faults. The largest block runs from 2012-03-26 08:25 to 2012-03-27 16:05 (381 steps). The test period is hit harder than train: 666 all-missing steps, or 9.7 % of its timeline, against 5.4 % for train. Consequences for later phases:

- Metrics must be **masked**, meaning steps where the true value is 0 are excluded. Otherwise every model gets "rewarded" or penalised for predicting outages.
- Lag and rolling features must treat 0 as missing, not as a speed. Any imputation must use only past values.

## Sensor graph

The files are in `sensor_graph/` of the same repo, loaded by `flowcast.data.metr_la.load_sensor_graph()`:

| File | Verified |
|---|---|
| `sensor_locations.csv` | 207 sensors, WGS84 lat 34.043–34.222, lon −118.537 to −118.183 (Los Angeles). Real coordinates are available for the map. |
| `adj_mx.npy` | 207×207 float32, values in [0, 1], self-loops = 1, 1,722 non-zeros, **directed (asymmetric)**. Thresholded Gaussian kernel exp(−d²/σ²) of road-network distance, with entries < 0.1 set to 0. |
| `adj_mx_mapping.json` | Sensor-id order of the adjacency rows, plus kernel parameters |
| `distances.csv` | 295,374 directed pairs (`from`, `to`, `cost` in metres) over 4,106 sensors. All 207 METR-LA sensors are present. |

**node_id → sensor_id mapping (assumption, empirically supported).** The windowed files contain only `node_id`. We map `node_id i` to `adj_mx_mapping.json["sensor_ids"][i]`, which is the DCRNN graph order and also the order of `sensor_locations.csv`. As a check, on training data only, the mean speed correlation of graph-connected pairs is **0.436**, against **0.204** for all sensor pairs. A wrong mapping would erase that gap.

## Memory profile

These figures were measured on the target machine (16 GB RAM):

- Raw Arrow per split: train 1,964 MB, validation 280 MB, test 561 MB, held as memory-mapped files and not copied into RAM.
- Reconstruction converts **one column at a time** (~40 MB each). The 2.8 GB of windows are never turned into a Pandas frame.
- Peak process working set: **~3.3 GB**. Most of this is memory-mapped file pages touched during the read, which the OS can reclaim.
- Canonical speed matrix: 54 MB in memory (float64), 9.6 MB as Parquet. Later phases only need this file.
- Runtime: ~33 s with a warm cache. The first download took ~90 s.
